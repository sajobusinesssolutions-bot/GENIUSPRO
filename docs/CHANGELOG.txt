GENIUS POS — WHAT'S NEW
================================

v1.47.0 (9 September 2026) — An Android app, against the hosted books
-----------------------------------------------------------------------

The same interface, wrapped as an installable Android app, talking to your
server, which talks to the hosted database. Three parts, and they are not
interchangeable:

    Android app  ─┐
                  ├─►  your server (Render)  ─►  Turso (the books)
    desktop till ─┘

WHY THE APP DOES NOT TALK TO THE DATABASE
Because it cannot be made safe. The database token is read-write access to
every shop's books, and an APK is a zip file whose strings anyone can read with
one command — shipping the token inside the app publishes it. The credentials
live in the server's environment and nowhere else. This is also the answer to
"Turso or Render": neither, both. Turso is a database and cannot run your code;
Render runs your code and has no database of its own.

BUILDING IT
  npx cap add android        # once
  npm run android:apk        # every build

Needs a machine with Android Studio. The web build runs first, so the app
always contains the same interface the desktop and browser get — there is one
codebase and the app is a shell around it.

FIRST RUN
The app opens on "Connect to your shop" and asks for the server's web address.
It checks the address really is a Genius POS server before saving it: one
mistyped character would otherwise turn into "wrong email or password" on every
attempt for the rest of the evening, which is an error about the wrong thing.
Asked once, changeable later under Settings → About & updates.

Building for a single known shop? Bake the address in and the screen never
appears:  VITE_API_BASE=https://yourshop.onrender.com npm run android:sync

NOTHING CHANGES FOR EXISTING INSTALLATIONS
With no address configured the interface talks to its own origin, exactly as it
always has. The browser and the desktop were served by the server they talk to,
so the question does not arise for them and the screen is never shown.

WHAT THE APP DOES NOT DO
It does not work offline. No connection means no sales, the same as a hosted
desktop till — there is no local copy on the phone and nothing queues to be
sent later. A shop with patchy signal should know that before staff rely on it.
It also has no camera, printing or push access yet; Capacitor makes those
reachable but none are wired up.

ALSO
  · render.yaml deploys against the hosted database now. The persistent disk is
    gone — there is no file to persist, and a file on one server was never
    going to be shared with a phone.
  · The phone counts as a device the account has not used before, so its first
    sign-in asks for the emailed code, then remembers it for thirty days.


v1.46.0 (9 September 2026) — A code to your email, once per device
-----------------------------------------------------------------------

An account signing in with an email address is now asked for a six-digit code
sent to that address — but only the first time a given computer or phone is
used. After that the device is remembered for thirty days and the password is
enough again.

Once per device rather than once per sign-in is the whole design. A code every
morning would cost a cashier several minutes at seven o'clock to defend against
something already defended against on that machine, and a shop whose till waits
on a mail server is a shop that switches the feature off. What this actually
stops is the thing worth stopping: a password used from somewhere else.

WHEN THE EMAIL DOES NOT ARRIVE
Ten single-use backup codes are shown once, when the account is created. Print
them and keep them where the shop keeps its papers. Without them, a mail outage
or a changed address is a business that cannot open its own books and a support
call with no good answer. Settings → Sign-in security prints a new sheet; doing
so stops the old one working.

WHAT IS NOT AFFECTED
PIN sign-in at the till is untouched. It is a shop-floor convenience for staff
standing at a counter, switched on per shop, and most counter staff have no
email address on file at all — the staff table has no email column. It follows
that PIN sign-in remains a way into a shop that does not pass through the code
step: on an installation where that matters, leave PIN sign-in switched off.

Staff signing in with a username and password are likewise unchanged, for the
same reason: there is no address to send a code to.

ALSO
  · Settings → Sign-in security lists every device that can skip the code, with
    when it was last used, and removes any you do not recognise. One button
    signs every device out for a laptop that has gone missing.
  · A password reset now clears the trusted devices as well as the sessions. A
    reset is what somebody does when they believe another person has their
    password; leaving that person's computer trusted would mean the reset
    locked the thief out of the password and left the way around it open.
  · Sign-up already emailed a code to confirm the address. It now also trusts
    the device that confirmed it, rather than asking for a second code on the
    very next screen.


v1.45.0 (8 September 2026) — The books can live online
-----------------------------------------------------------------------

Until now a shop's books were a file on one computer, and the Sync screen
moved a copy of that file between machines: one book, one place at a time.
Two people could take turns; they could not both sell at once.

This version adds a second way to keep them. Point the app at a hosted SQLite
database (Turso / libSQL) with two settings and there is one live database
that every till and phone reads and writes directly. A sale rung up at the
counter is on the phone in the back office the moment it is saved. Nothing is
uploaded or brought down, because there is nothing to move.

    GENIUS_DB_URL=libsql://your-shop.turso.io
    GENIUS_DB_TOKEN=…

Existing installations are untouched. With those unset, everything behaves
exactly as before, down to the same file in the same place.

WHAT IT COSTS
The till needs a connection. With the books in a file a broken line was
somebody else's problem; hosted, a till that cannot reach the database cannot
sell. There is no offline copy yet. If the shop's internet is unreliable, the
file is still the better arrangement — the guide says so plainly rather than
selling the new thing.

The daily whole-file backup also stops, because there is no file on that
computer to copy. Backups become the hosting provider's, and the Sync screen
and the log both say so instead of quietly copying nothing. "Download a copy"
still works, so a shop is never locked in.

MOVING AN EXISTING SHOP UP
  node backend/tools/books-online.js --from backend/data/genius.db \
       --to libsql://your-shop.turso.io --token … --dry-run

It never writes to the local file, refuses a destination that already holds
rows, and copies one transaction per table. Full guide in
docs/HOSTED-DATABASE.md.

UNDER THIS
Every database call in the application became a promise, because a call across
a network cannot be made to look like one into memory. That is 527 functions
and about 2,000 call sites, done mechanically and checked mechanically. Three
faults were found and fixed on the way, all of which predated or would have
been introduced by that change:

  · the idempotency guard on sales, returns and the till (`findByRef`) was
    left un-awaited by the first pass. A promise is always truthy, so every
    sale would have been answered "already recorded". Found by a name-based
    sweep for calls the call graph could not resolve, and fixed.
  · several screens ran one query per row — the trial balance ran a SELECT per
    account, the sales-by-item report one per sale. Harmless against a file,
    a hundred round-trips against a hosted database. Both are now single
    grouped queries.
  · the test runner started every async test at once while claiming to run
    them one at a time, so suites sharing a database interleaved. It now runs
    them in order, which is what it always said it did.


v1.42.0 (3 August 2026) — Modules, part 4: Tax & URA
-----------------------------------------------------------------------

Five tabs: the VAT working, a checklist to run before filing, the EFRIS
register, withholding, and what has been filed.

WHAT THIS SCREEN DOES NOT DO
It does not file anything and it does not send to EFRIS. It works the figures
out from your own documents and keeps the record of what you did elsewhere.
Every screen that could be mistaken for a submission says so plainly, because
a shop that thinks it has filed and has not is a shop with a penalty coming.

It also does not state a legal deadline. The due day is a setting, and the
screen tells you to check it against the current URA deadline. Deadlines
change; an app that asserts one with confidence is the app that gets blamed.

THE VAT WORKING
Output VAT less input VAT, shown as a worksheet — sales, VAT charged, credit
notes, purchases, input VAT, answer — so you can see how the figure was
reached rather than being handed it. It prints as a working paper.

If URA owes you rather than the other way round, it says so and colours it
differently. A refund shown as a bill to pay is worth getting right.

WHAT YOU CANNOT CLAIM
The number this screen exists for. Input VAT on bills with no supplier TIN
cannot be claimed, so it is excluded from the return — and then reported
separately, with the bills named, because that is money the shop paid and can
often still recover by getting the TIN.

BEFORE YOU FILE
A checklist: bills with no supplier TIN, large invoices with no customer TIN
(a registered buyer will come back asking), invoices with no fiscal number,
and whether your own TIN is on file at all. Each names the documents. A count
cannot be fixed; a list can.

EFRIS
A register of what happened on EFRIS, per invoice. Record the fiscal number,
a rejection and why, or mark an invoice as not needing one. Marking something
as sent requires the fiscal number — without it there is nothing to reconcile
later, and it may as well not have been sent.

WITHHOLDING
Both directions, kept apart because they are easy to confuse: tax you withheld
from a supplier and now owe URA, and tax a customer withheld from you, which
is money already paid on your behalf. A supplier whose TIN is missing is
flagged, since they cannot be given a certificate.

FILING HISTORY
Every period for the last year, filed or not, so a missed month shows as a gap
rather than being absent. On time, late or overdue is judged against your own
due date, and the next one due is at the top.

ONE THING WORTH KNOWING
If you have more than one tax set up — VAT and a local levy, say — only VAT
goes into the VAT return. The app needs to know which of your taxes is VAT;
it assumes one called "VAT" and you can change that under Settings → General.
If no such tax exists the screen says so, rather than showing a return of zero
that looks like a quiet month.

v1.41.0 (3 August 2026) — Modules, part 3: Staff
-----------------------------------------------------------------------

The Staff entry used to open a second copy of the user list — the same
accounts and roles that Settings already manages properly. It now opens
something that did not exist before: what the team actually did.

Three tabs.

ON TODAY
Every shift opened today: who, when they came in, when they left, hours so
far, how many bills they rang up and what those came to. Across the top, the
figure worth knowing — what an hour of staff time brought in.

Anyone rostered who has not opened a shift is listed underneath. Anyone who
came in later than their rostered start, by more than the few minutes you
allow, is marked late on their row.

Shifts are the only arrival this app can honestly witness — they are opened at
the till. There is no clock-in from a phone because there is no phone app, and
inventing one would mean recording arrivals that never happened.

WHAT THEY SOLD
Per person, per month: bills, sales, average bill, discount given, what came
back, net, and sales per hour worked.

Returns count against whoever made the original sale, not whoever happened to
process the return. The person who handled the return did not cause it.

WHAT THEY ARE OWED
Commission, at last, as a real feature.

Until now the only commission in the app was a percentage you typed into a
report to see a number. That number could not be paid out, could not be
audited, and vanished when the page closed.

Commission is now a rate stored against each person, with a shop-wide default
for everyone who does not have their own. Set both under Terms on this screen
and Settings → General.

It is earned on NET sales — sold, less returned. Paying on gross would mean a
sale returned the next day still earned its commission, which is exactly how a
commission scheme gets gamed. Each row shows the clawback where returns have
eaten into it.

ROSTERED HOURS
Set a start and end time per person. This is what "late" and "absent" are
measured against — without them nobody can be late, because there is nothing
to be late for. The grace period is under Settings → General.

WHAT IS NOT HERE
Payroll, PAYE and NSSF. Those need statutory rates and bands that change by
law and by year, and a number this app invented is a number somebody might
file with URA. Commission is calculated and shown as owed, and stops there.

v1.40.0 (3 August 2026) — Modules, part 2: Instalments and Loyalty
-----------------------------------------------------------------------

Both have moved into Sales as tabs, the same way Recurring did. A payment plan
is a sale collected in pieces, and loyalty points are earned by selling — a
shopkeeper looking at sales should not have to leave to find either.

Old links still work and land on the right tab.

INSTALMENTS
Three sub-tabs: Due Soon with a count of who is behind, All Plans, and
Payment History.

Across the top: what is still to collect, and — when anyone is behind — what
is overdue right now, in red. When nobody is behind, that second figure
switches to what is expected this month instead, since there is no point
shouting about arrears that do not exist.

• Due Soon lists each instalment that has fallen due, whose it is, how late,
  and a button to take the money.
• All Plans shows each plan's shape (4 × monthly, deposit paid), how much has
  come in as an amount and a percentage, when the next payment falls, and
  whether it is on track or in arrears.
• Setting up a plan shows the whole schedule, every date and amount, before
  you commit. The dates come from the server, so what you approved is what
  gets saved.

One thing worth knowing: an instalment is not paid as its own document. Money
is recorded against the invoice in the ordinary way, and the schedule settles
the earliest unpaid instalment first. That is why the plan can never disagree
with the books — there is only one place money goes in.

LOYALTY
Three sub-tabs: Can redeem, All Members, and Points History.

"Can redeem" is first because it is the useful one: a customer who does not
know they have points does not come back for them.

Across the top: points outstanding, and what they would cost you if everyone
redeemed at once. That second figure is a real liability and was not visible
anywhere before.

The scheme is spelled out in words above the list — one point per so much
spent, what a point is worth, the minimum to redeem, whether they expire.

Redeeming records that the points were spent and says, plainly, that taking
the money off the bill still happens at the till. A shopkeeper who assumes
otherwise hands over the discount twice.

Adjusting a balance by hand requires a reason, and records who did it.

TABS FOR SWITCHED-OFF FEATURES
Recurring, Instalments and Loyalty only appear when switched on under
Settings → Modules. Previously the Recurring tab showed regardless, which is a
tab that leads nowhere.

34 unit tests still pass.

v1.39.0 (3 August 2026) — Fixes
-----------------------------------------------------------------------

REPORTS WOULD NOT OPEN
The screen crashed the moment it was clicked. When the Reports screen was
rebuilt, a block of settings was deleted that took six values with it — the
list of report groups among them — while the code that reads them stayed
behind. Restored.

ITEM SEARCH AND "ADD A CUSTOMER" DID NOTHING
This was one fault behind most of what felt broken: creating an invoice,
recording a purchase, setting up a recurring sale, and building an instalment
plan.

Search results and the add-a-customer dialog were opening *behind* the panel
that asked for them. They were there the whole time, underneath. The panels
introduced during the redesign sat higher than the lists and dialogs they
open, and nothing catches that — it does not break the build and it does not
throw an error; the thing simply appears where you cannot see it.

Everything that opens on top of something else has been put in one order:
panel, then dialog, then dropdown, then confirmation, then notices. There is
now a check that fails if that order is ever broken again.

SECOND UNIT LEFT THE QUANTITY AT 1
Selling a bag as loose kilos should turn 1 bag into 50 kg. If you had clicked
into the quantity box first, it stayed at 1.

The quantity box was holding what you had typed and writing it back when it
lost focus — which happened *after* the unit changed, so it overwrote the
conversion. The box now discards what it was holding when the value changes
underneath it, and the unit buttons act before the box lets go rather than
after.

NEW PRODUCT AND NEW SERVICE
• Products now ask whether to count stock. Airtime, printing and
  anything bought to order is sold but not counted, and the app was assuming
  every product was counted.
• Barcodes are gone from the service form, and the stock fields with them.
• Choosing "service" or "not counted" hides everything that no longer applies
  rather than leaving dead fields on screen.

BETTER ERRORS
A form that left out a required field got back "Server error" with a reference
number. The database refused the empty value before the form's own checks
could run. Missing fields are now treated as empty, so you get "Choose an
invoice" or "Choose a customer first" — the message that was written for it.

CHECKED END TO END
Creating a counted product, an uncounted product and a service; selling each
at the till; selling in both units; a credit invoice; a purchase in both
units; a recurring sale and a recurring purchase; and an instalment plan.
Stock arithmetic balances exactly — a 50 kg sale takes one bag off the shelf.

v1.38.0 (3 August 2026) — The forms that were left behind
-----------------------------------------------------------------------

Screens were rebuilt one at a time, but the forms and dialogs inside them
often were not. The result was a screen in the new look opening a dialog in
the old one. This closes that gap.

HOW IT WAS DONE
Rather than hand-convert nine forms and inevitably miss one, the shared
pieces every form is built from — the dialog frame, labels, inputs, buttons,
tables, totals blocks — were restyled once. Every form that uses them picked
up the new look at the same moment, and the next form written will get it for
free rather than needing the same work again.

WHAT THAT COVERS
• Recording a purchase bill, including the order picker and the extra-costs
  block.
• Debit notes and expenses.
• Settings → Taxes: the chain on the left, and what it does to a real bill on
  the right, so you can see the effect of a rate before saving it.
• Settings → Price lists, Print, Backup, About and the updater.

A DUPLICATE REMOVED
Settings had its own Units and Item categories editors — a name, and a button.
The Items screen has proper ones: how many items use each unit, which
conversion pairs are actually in use, what each category holds in stock, and a
colour per category.

Two places to add a unit, one of them worse, is a trap: you use the thin one,
wonder why it tells you nothing, and never find the good one. Settings now
sends you to the Items screen for both. Party groups stay in Settings, since
they have nowhere else to live.

BACKUP
Split into two plain halves — take a copy, and put one back — instead of one
column with the restore control tucked underneath. What restoring will do, and
what you would lose, is still shown before anything happens.

v1.36.0 (3 August 2026) — Modules, part 1: Recurring
-----------------------------------------------------------------------

WHERE IT LIVES NOW
Recurring has stopped being a screen of its own. Recurring sales are a tab in
Sales; recurring purchases are a tab in Purchases. They are sales and
purchases — a shop looking at its sales should not have to leave to find the
ones that repeat.

Old links and search results still work; they land on the right tab.

SETTING ONE UP
The same invoice screen as a normal sale — same customer picker, same item
table, same tax and unit handling — with a Recurring Schedule block at the
foot: a description, how often, and the date to start. There is a switch for
whether the schedule is live, so you can build one now and turn it on later.

Reusing the invoice screen is the point. A recurring sale that calculated tax
or units differently from a one-off would be a bug waiting to happen, and
that is exactly what a second, separate form invites.

The first document is raised on the start date, not when you save. Nothing
touches stock or the books until it actually runs.

THE LIST
Three sub-tabs, smaller than the tabs above them so the nesting reads as
nesting:
  • Due Soon, with a count when anything is waiting
  • All Schedules
  • Payment History — everything these schedules have actually raised

Above them, two figures: projected monthly revenue, and what is still expected
this month. The projection converts everything to a monthly figure so a weekly
schedule and a yearly one can be added together honestly. "Expected this
month" counts every run still to come before month end, not just the next one
— a weekly schedule bills four more times, not once.

Both figures are subtotals before tax, deliberately. Tax varies by party and
by item, and a projection that is confidently wrong is worse than one that is
plainly a subtotal.

Days Left says what it means: "2 days overdue" in red, "Due today", "5 days
left". A paused schedule shows nothing there rather than counting down to a
date it will not act on.

From any row: raise it now, pause it, edit it, or delete it. Deleting stops
the schedule and leaves everything it has already raised alone.

A run that fails is recorded as a failed run with the reason, and shows in
Payment History. A schedule that cannot bill — because the price is below cost,
say — should say so, not fail silently.

FIXED
The "Invoice builder" entry in the menu opened the invoice list rather than
the builder.

v1.35.0 (3 August 2026) — Design deck, session 14: Sign in
-----------------------------------------------------------------------

THE SCREEN
Two panels. On the left, what the app is and what it does, with your business
name and the version running. On the right, signing in. On a narrow screen the
left panel drops away — it is a description the person has already read.

SIGNING IN WITH A PIN — NEW
Four digits instead of a password. At a counter, typing a full password every
time somebody swaps shifts is a nuisance people work around by sharing one
login, which is worse than the problem.

  • PINs are set per person under Settings → Users & roles.
  • They are stored scrambled, exactly like passwords. Nobody can read one
    back afterwards, including whoever set it.
  • Obvious PINs are refused — 1234, 0000, 1111 and the like are the first
    anyone would try.
  • Signing in with a PIN still needs the username alongside it. Four digits
    on their own is ten thousand guesses, and the only thing standing in the
    way would be the lockout counter.

THE STAFF PICKER — NEW, AND OFF BY DEFAULT
Names and roles on the sign-in screen, so somebody taps their name instead of
typing a username.

This is genuinely quicker at a busy counter. It also tells anyone standing in
front of the screen who works here and what each of them does, before they
have signed in to anything. That is a reasonable trade in a shop and a bad one
in an office, and it is not our call to make — so it is off until you switch
it on under Settings → General, and so is PIN sign-in.

WHAT WAS NOT BUILT, AND WHY
The design also shows a "scan QR from the phone app" button and a list of
companies on this device with sync status. There is no phone app to scan from
and no sync to report on, so neither is there. A button that does nothing is
worse than a button that is missing.

"Trust this counter for 30 days" is likewise absent: it needs a device
identity and a token that outlives a session, which is a security design
rather than a switch.

v1.34.0 (3 August 2026) — Design deck, session 13: Settings & permissions
-----------------------------------------------------------------------

THE SHELL
Every settings subject down one list on the left, the page open beside it.
The old grid of coloured tiles cost a click to reach anything and gave no
sense of what else was there.

Save and Discard sit at the top and say how many changes are waiting, so you
always know whether you have unsaved work. Pages that save one thing at a time
— taxes, price lists, roles, printing — keep their own buttons rather than
pretending to belong to a page-wide save.

Settings for features you have switched off no longer appear in the list.

USERS & ROLES — NEW
Two views. Staff accounts: add someone, give them a role, switch an account
off when they leave. And what each role may do.

PERMISSIONS IN PLAIN ENGLISH
The permission screen now asks questions — "Give a discount", "See cost price
and margin", "Write off a debt", "Delete all data" — 36 of them across seven
groups. Nobody setting up a shop thinks in terms of "sales.create"; they think
in terms of what the person at the counter is allowed to do.

Each question maps to the permissions the server actually checks, and that
mapping lives on the server. This matters more than it sounds: if the screen
kept its own list, a permission could show as allowed here while the app
refused it in practice, and nobody would know why. Every permission the app
enforces is reachable from this screen, and nothing on this screen grants
something the app does not enforce. That was checked, not assumed.

TWO THINGS THE SCREEN NOW REFUSES TO DO QUIETLY
• It will not let you remove user management from the last role that has it.
  A shop that locks itself out of its own user list cannot get back in.
• If a role holds half of what a question needs — say it can add a customer
  but not edit one, where the question covers both — the question reads as
  blocked, and saving would drop the stray half. The screen now says so, in
  words, before you save. It used to be that this simply happened.

ABOUT THE MIDDLE SETTING
The design offers three states: allowed, needs a nod, and blocked, where
"needs a nod" means a manager approves at the moment it happens. Nothing in
the app can ask for that approval — it would need a prompt everywhere it
applies and a record of who approved what. So the screen offers two states and
says why, rather than showing a third that quietly did nothing. The
permissions where an approval step would make sense are already marked in the
code for whenever that gets built.

v1.33.0 (31 July 2026) — Design deck, session 12: Stock take
-----------------------------------------------------------------------

Three tabs: the count you are working on, the ones you have finished, and what
all that counting has actually been telling you.

COUNTING NOW
Across the top: how far through you are, how many matched, how many differed
and which way, and what posting the count would do to the value of your stock.
That last figure moves as you type, so you know before you commit.

The sheet itself shows system against counted, the difference, and what the
difference is worth. Blank lines are drawn as blank, not as zero — an item you
have not reached yet is not an item you counted as none. Scan a barcode to
jump to a line and start typing. "Differences only" hides everything that
matched once you have worked through a section.

Two helpers at the foot: save a draft, or fill the blanks with what the books
already say. The second asks first and says plainly that it is not the same as
counting those shelves.

POSTING — WHAT CHANGED AND WHY
A count that differs now has to say why: spoilage, theft, a keying error,
breakage, or a genuine recount. And which expense account the write-off should
land in.

Until now every count landed in one bucket. That meant that months later,
"the shop is losing stock to theft" and "somebody keyed a delivery wrong"
looked identical in the books, and nothing could be done about either. Posting
without a reason is now refused.

Both the reason list and the account are checked on the server, so a count
cannot be filed under something the books do not recognise.

VARIANCE REPORT
The new tab. Which items keep coming up short, how many times each was counted
and how often it was wrong, and what it has cost in shillings — with the same
totals grouped by the reason given. An item that is short every single time is
a different problem from one that was short once, and this is the only view
that can tell them apart.

PAST COUNTS
Every count with who ran it, what it covered, the reason given and its value
effect. A draft can be abandoned; a posted count cannot be deleted, because it
has already moved stock and written to the ledger — count again to correct it.

v1.15.0 (26 July 2026) — Warranty cover & claims
--------------------------------------------------
The last of the new modules. Switch on "Warranty cover & claims" in
Settings → Modules, then set a warranty period in months on any item.

• Selling a covered item registers the cover by itself — tied to the customer,
  the invoice and the date, running for the item's own period. Cover is
  created inside the sale's transaction, so a refused invoice never leaves
  cover behind.
• Serialised items get one record per unit, so an individual radio or phone
  can be traced rather than a whole line of them.
• Serial lookup sits at the top of the screen, because that is how this
  actually gets used: a customer walks in holding the thing and you need to
  know in seconds whether it is still covered, and until when.
• Cover shows as in cover, ending soon (within a month), expired or void, so
  a unit about to run out is visible before the customer finds out the hard
  way.
• Claims record the fault, and close as repaired, replaced, refunded or
  rejected with what settling them cost. A claim outside the cover period is
  refused and the message says when cover ran out, rather than quietly
  accepting a promise the shop cannot keep.
• Cover can be voided with a reason, and the record stays so the history is
  still explainable. Nothing can be claimed against voided cover.
• Cover for goods sold before the module was switched on can be registered by
  hand.

Cover periods handle short months properly: something sold on 31 January with
one month of cover runs to 28 February (29th in a leap year).

v1.14.0 (26 July 2026) — Loyalty points
-----------------------------------------
Switch on "Client loyalty points" in Settings → Modules for a Loyalty page,
and set the scheme up under Settings → Loyalty.

• Customers earn points automatically when a sale is billed to them — one
  point per however many shillings you choose. Walk-in "Cash Sale" business
  earns nothing, since there is nobody to credit.
• Points are awarded inside the sale's own transaction, so an invoice that
  fails can never leave points behind.
• Every movement is a row in a ledger — earned, redeemed, corrected, expired —
  and a balance is simply their sum. Nothing caches a running total, so a
  balance can always be explained by the movements behind it, right back to
  the sale that caused it.
• Redeeming gives you the shilling value to take off the bill as an ordinary
  discount, so the money side stays in the invoice where the books can see it.
  A minimum redemption keeps small balances from being fiddly.
• Corrections need a reason, and the reason stays in the customer's history.
• Points can be set to lapse after a number of months. The expiry sweep treats
  older points as spent first, so a customer who keeps earning and redeeming
  never loses points they have effectively already used.
• The members list shows what the scheme owes customers in shillings — useful
  to know before running a promotion on top of it.

v1.12.0 (26 July 2026) — Manufacturing
----------------------------------------
Switch on "Manufacturing" in Settings → Modules for recipes and production runs.

• A recipe (bill of materials) says what goes into one batch: the components
  and their quantities, how many finished units a batch yields, and the labour
  and overhead a batch costs. Recipes can be retired and put back in use.
• Before producing, the costing panel shows exactly what the run will consume,
  what each component is worth, what the batch costs in total, and what each
  finished unit will therefore cost. No surprises after the fact.
• Producing takes the components off the shelf and puts the finished goods on
  it carrying their real cost — so the margin on what you make is as honest as
  the margin on what you buy.
• Short of stock, production is refused and the message names exactly what is
  missing and by how much, rather than driving stock negative.
• Every run keeps a record of what it ate and at what cost, so a finished
  item's price can always be explained months later.
• Components turning into product is value moving within inventory, so it
  needs no journal entry. Labour and overhead are money genuinely spent, and
  those do raise the value of what is now on the shelf — the books balance
  either way.
• Sensible refusals: a recipe cannot contain the item it produces, the same
  component cannot be listed twice, and a recipe already used in production is
  retired rather than deleted so past runs still make sense.
